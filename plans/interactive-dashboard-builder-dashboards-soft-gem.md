# GalaxyData — Interactive Dashboard Builder

## Context

GalaxyData Manager browses, edits and queries data, but has no way to present it. We are adding dashboards (like Superset's and Grafana's) that users build and manage themselves:

- a responsive grid of widgets (Text, Pie, Bar, Line, Table to start; more kinds later);
- each chart builds a GDQ query from a configuration (data source, columns, aggregation, display mapping), never from text the browser sends;
- built-in filters, and runtime filters set by clicking slices, so one chart drills down the charts linked to it, across sources linked by a relation too;
- private, shared, or public: a public dashboard has an unguessable link, embeddable in an iframe on another site, viewable without signing in;
- shared and public dashboards have a working copy (only its owner sees it) and published revisions (what everyone else sees);
- manual refresh by default, or on a timer.

The engine, the server (B0–B8) and the client (F0–F10) are built ([federated-query-engine-and-kind-flame.md](federated-query-engine-and-kind-flame.md)). This plan adds milestones D0–D9 on branch `feature/dashboard`, in the same conventions: 3-space indents, Allman braces, file-scoped namespaces; minimal APIs with typed results and problem codes; EF migrations; signals, signal forms and lazy features in the client; golden snapshots, fast-check and Material harnesses in tests.

**Decisions confirmed with the user**
- **Charts: Apache ECharts** (tree-shaken, loaded lazily with the dashboard pages). **The grid is our own:** a pure TypeScript layout engine, plus pointer and keyboard drag and resize.
- **Breakpoints:** the widest layout is the one designed. Narrower widths are derived (widths scaled to the column count, then packed in reading order). The editor can switch to a narrower width and adjust it, which saves an override for that width alone.
- **Sharing:** with chosen users, or with everyone signed in. Viewers see the published copy; only the owner edits. Administrators manage shared, public and orphaned dashboards, as they do saved queries.
- **Public:** only data managers and administrators make a dashboard public. `Dashboards:AllowPublic` turns public dashboards off altogether. Making a dashboard public, regenerating its link and revoking it are written to the admin audit.

**Out of scope (later):** dashboard-local query sources (a data source is a catalog entity: a table, a view, or an overlay virtual entity), widgets built from GDQ text, editing by anyone but the owner, scheduled exports, alerts, KPI and map widgets (the registry makes room for them).

## 1. The definition (what a revision holds)

One JSON document, typed on both sides: C# records in `GalaxyData.Web/Dashboards/Definition.cs`, written to OpenAPI, and `Schema<…>` types in the client. Widget configs are polymorphic by the `kind` inside them (`[JsonPolymorphic]`, `AllowOutOfOrderMetadataProperties`; an unknown kind is a malformed request, 400, naming its path): `{"id": "w2", "title": …, "config": {"kind": "bar", …}}`. Ids are `[a-z0-9-]{1,32}`, unique within their list.

```jsonc
{
  "schema": 1,
  "layout": {
    "rowHeight": 48, "gap": 12,
    "breakpoints": [ { "id": "narrow", "label": "Narrow", "minWidth": 0, "columns": 1 },
                     { "id": "medium", "label": "Medium", "minWidth": 720, "columns": 6 },
                     { "id": "wide", "label": "Wide", "minWidth": 1200, "columns": 12 } ],   // ascending; the last is designed
    "items": { "w1": { "x": 0, "y": 0, "w": 12, "h": 2 } },
    "overrides": { "medium": { "columns": 6, "items": { "w1": { "x": 0, "y": 0, "w": 6, "h": 2 } }, "hidden": [] } }
  },
  "sources": [ { "id": "orders", "entity": "shop.orders", "label": "Orders" },
               { "id": "customers", "entity": "shop.customers", "label": "Customers" } ],
  "links": [ { "from": "orders", "to": "customers", "path": ["customer"] } ],   // navigations from `from`'s entity to `to`'s; a forest
  "filters": [ { "id": "country", "label": "Country", "field": { "source": "customers", "path": [], "column": "country" },
                 "kind": "values", "value": { "op": "in", "values": ["ZA"] },
                 "visible": true, "editable": true, "multiple": true, "except": [] } ],
  "widgets": [
    { "id": "w1", "title": null, "config": { "kind": "text", "markdown": "# Sales" } },
    { "id": "w2", "title": "Orders by status", "config": { "kind": "bar",
        "source": "orders",
        "dimension": { "field": { "path": [], "column": "status" }, "bucket": null, "label": "Status" },
        "series": null,
        "measures": [ { "aggregate": "count", "field": null, "label": "Orders" },
                      { "aggregate": "sum", "field": { "path": [], "column": "total" }, "label": "Revenue" } ],
        "sort": { "by": "measure", "index": 0, "descending": true }, "limit": 25,
        "conditions": [], "emits": true, "listens": "all",
        "display": { "orientation": "vertical", "stack": "none", "legend": "bottom", "labels": false, "numberFormat": null } } }
  ],
  "refresh": { "mode": "manual" },          // or { "mode": "interval", "seconds": 300 }
  "public": { "showData": true }
}
```

- **Fields** are `{path, column}` on a source: `path` holds forward (one or zero-or-one) navigations, so `customer.country` on orders is `{path: ["customer"], column: "country"}`. **Labels are stored** (the editor fills them from column labels at save), so public answers never need column names.
- **Aggregates:** `count` (rows), `countValues` (written `count(r0 => r0.x != null)`, as `count(x)` of a boolean counts its trues), `countDistinct`, `sum`, `avg` (numbers), `min`, `max` (ordered types, not booleans). Sums and averages through a navigation path are a warning ("each customer counts once per order").
- **Buckets** for date and date-time dimensions: `day` (`date(x)`), `week`, `month`, `quarter`, `year` (D0's `startOf…`), and the cyclic `quarterOfYear`, `monthOfYear`, `dayOfWeek`, `hourOfDay`. A date-time dimension must have a bucket (raw instants don't compare safely through the merge engine, which keeps microseconds).
- **Conditions** (filters' values and widgets' own) are `{field, op, value?, valueTo?, values?, relative?}` with `op` one of the grid's (`eq`, `ne`, `lt`, `le`, `gt`, `ge`, `between`, `contains`, `notContains`, `startsWith`, `endsWith`, `blank`, `notBlank`) plus `in`, `notIn` and `relative` (`{unit: day|week|month|quarter|year, count, mode: last|this|previous|toDate}`). Values are as `ValueCodec` writes them, for the field's type.
- **Filter kinds:** `values` (`in`/`notIn`), `range` (`between`, `ge`, `le`; dates by day on date-times), `relative`, `text` (`contains`, `startsWith`), `boolean`. `visible` and `editable` give the four kinds the spec asks for (hidden, read-only, configurable; a hidden filter is never editable). `except` lists widgets it doesn't apply to.
- **Per kind:** pie (`dimension`, one measure, `limit`, `other`, `donut`, `labels`), bar (`dimension`, optional `series`, measures (one when there is a series), `orientation`, `stack: none|stacked|percent`), line (`dimension` as x, `series`, measures, `area`, `gaps: zero|connect|break`), table (`mode: grouped|raw`; grouped: dimensions and measures; raw: `columns` of fields; `sort`, `pageSize`), text (`markdown`, ≤ 20,000 characters). Every data widget has `conditions`, `emits`, `listens` (`all`, `none`, or widget ids).
- **Limits** (`Dashboards:*`, checked on save): 50 widgets, 20 sources, 30 filters, 256 KB of JSON, 500 values in a condition, 1–24 columns, interval refresh at least `MinRefreshSeconds` (30).
- **Structure is checked on save** (400 by JSON path: `definition.widgets[2].config.measures[0].aggregate`): ids, references between lists, kinds, limits, breakpoints ascending from 0, links forming a forest. **The catalog is checked when shown and run**: entities, columns, navigations and types may change after a save, so those are **issues** per widget (code, severity, message, field) in the dashboard's answer and in previews, never a refusal to save, as overlay items are.
- **Canonical form:** the server serializes the validated model with sorted keys and normalized numbers (as saved queries do), and hashes it (SHA-256). Equal hashes mean nothing changed: no-op saves, and "unpublished changes".

## 2. Engine: date buckets (D0)

`FunctionId` gains `StartOfWeek`, `StartOfMonth`, `StartOfQuarter`, `StartOfYear` (each `date`, nullable as its argument) and `Quarter`, `DayOfWeek` (`int32`; ISO: Monday 1 to Sunday 7), registered in `FunctionRegistry` as `date` is (`DateLike(a, 0)`), and written in every dialect. Weeks start on Monday. Date-times with offsets are taken in UTC, as `year()` and `date()` already are.

| Function | PostgreSQL | SQL Server 2016+ (`u` = `Utc(c)`, `d` = `CAST(u AS date)`) | SQLite | DuckDB (`t` = `CAST(x AS TIMESTAMP)`, UTC sessions) |
|---|---|---|---|---|
| `startOfWeek` | `CAST(date_trunc('week', x) AS date)` | `DATEADD(day, -((DATEDIFF(day, '1900-01-01', d) % 7 + 7) % 7), d)` (1900-01-01 was a Monday; no `@@DATEFIRST`) | `date(x, '-6 days', 'weekday 1')` | `CAST(date_trunc('week', t) AS DATE)` |
| `startOfMonth` | `… 'month' …` | `DATEFROMPARTS(YEAR(u), MONTH(u), 1)` | `date(x, 'start of month')` | `… 'month' …` |
| `startOfQuarter` | `… 'quarter' …` | `DATEFROMPARTS(YEAR(u), (DATEPART(quarter, u) - 1) * 3 + 1, 1)` | `date(x, 'start of month', '-' \|\| ((CAST(strftime('%m', x) AS INTEGER) - 1) % 3) \|\| ' months')` | `… 'quarter' …` |
| `startOfYear` | `… 'year' …` | `DATEFROMPARTS(YEAR(u), 1, 1)` | `date(x, 'start of year')` | `… 'year' …` |
| `quarter` | `EXTRACT(QUARTER …)` | `DATEPART(quarter, u)` | `(CAST(strftime('%m', x) AS INTEGER) + 2) / 3` | `CAST(quarter(t) AS INTEGER)` |
| `dayOfWeek` | `EXTRACT(ISODOW …)` | `(DATEDIFF(day, '1900-01-01', d) % 7 + 7) % 7 + 1` | `(CAST(strftime('%w', x) AS INTEGER) + 6) % 7 + 1` | `CAST(isodow(t) AS INTEGER)` |

- PostgreSQL takes `timestamptz` at time zone UTC (sessions already work in UTC); SQLite's date functions read an offset and convert to UTC, as its `year()` does; DuckDB's cast avoids the ICU-only `date_trunc(TIMESTAMPTZ)` and covers `TIMESTAMP_NS`; SQL Server's `Utc` is the `SWITCHOFFSET` its `year()` uses.
- **Tests:** the six functions in `Conformance.Queries` (on `order_date` and the offset `placed_at`, and a `groupBy` by bucket), which feeds SQLite against DuckDB, the servers, sources split and the merge engine alone, and the fuzzing; `ServerEdgeTests.FunctionCases` on `d`, `ts` and `z` (the probe rows cross UTC month and year lines) with **hand-computed expectations** (a bug every database shared would pass the comparisons: `2026-01-31 23:30-05:00` → 2026-02-01; `2026-12-31 22:00-03:00` → 2027-01-01; the week of 2024-02-29 starts 2024-02-26; a Sunday is 7); `SqlServerMergeCases`; `PlanCases` (golden SQL per dialect); the binder's error snapshot (`startOfMonth(status)`).
- **Docs:** `docs/language.md` §8.3 rows and notes, a `gdq` example (`shop.orders.groupBy(m: startOfMonth(order_date)).select(m, n: count()).orderBy(m)`) and a `gdq-error` one; `LanguageDocTests` requires each.

**Built in D0**
- `FunctionId` gains the six (appended); `FunctionRegistry` registers them after `daysBetween` (`startOf…`: `date`, nullable as the argument; `quarter`, `dayOfWeek`: `int32`).
- **Dialects:** DuckDB `StartOf`/`Instant` (a date as it is, anything else `CAST(… AS TIMESTAMP)`); PostgreSQL `StartOf` (a date cast to `timestamp`, an offset `AT TIME ZONE 'UTC'`), `EXTRACT(QUARTER|ISODOW …)`; SQL Server `DATEFROMPARTS` and day counts from 1900-01-01 (`DateOf`: a date as it is, else the UTC date), so neither `@@DATEFIRST` nor the language matter; SQLite `date()` modifiers (`'-6 days', 'weekday 1'`, `'start of month'`, `'start of year'`) and `strftime` arithmetic.
- **Tests:** four conformance queries (dates, offsets, groups by bucket); `ExecutionTests.DateBucketsAreTheFirstDaysOfTheirPeriods` (hand-computed, SQLite, DuckDB, and SQLite through the merge engine: a leap day, Sundays, weeks across a year's end, offsets whose UTC day is in another month, quarter or year); two plan cases (golden SQL per dialect, lowering); the binder's error for `startOfMonth(status)`; on the servers `date-buckets`, `date-bucket-groups` and `dto-buckets` against SQLite, `DateBucketsAreTheFirstDaysOfTheirPeriods` by hand (and SQLite's own, which runs without servers), and seven merge-engine cases (PostgreSQL `timestamptz`, `timestamp`, `date`; SQL Server `datetime`, `datetimeoffset`, `smalldatetime`).
- **Results:** engine 489, integration 532, containers 451 (none skipped), all passing.

## 3. Server (`GalaxyData.Web`)

### 3.1 Model (migration `Dashboards`)
- **`Dashboards`** (`IVersioned`): `Id`; `OwnerId?` (FK Users, `SET NULL`: a deleted owner's dashboards stay, as saved queries do) and `OwnerName`; `Name` (200, `NOCASE`, unique per owner); `Description`; `WorkingJson`, `WorkingHash`; `PublishedJson?`, `PublishedHash?`, `PublishedNumber?`, `PublishedAt?`, `PublishedByName?` (the published copy lives on the row: no circular key, and pruning revisions can't remove it); `SharedWithEveryone`; `PublicToken?` (unique; 128 random bits, base64url, no dots), `PublicEnabledById?` (`SET NULL`), `PublicEnabledByName`, `PublicEnabledAt?`; `EmbedOriginsJson?`; `CreatedAt`, `UpdatedAt`, `Version`.
- **`DashboardShares`** (`DashboardId`, `UserId`), both cascading; indexed by user.
- **`DashboardRevisions`**: `DashboardId` (cascade), `Number` (unique per dashboard), `DefinitionJson`, `Hash`, `PublishedAt`, `PublishedById?`, `PublishedByName`, `Note` (200). The newest `Dashboards:KeepRevisions` (20) are kept, pruned in the publish's save.
- **No stored visibility:** private, shared (everyone or chosen users) and public (a token) are derived, so they can't contradict each other. Unpublished changes: `WorkingHash != PublishedHash`.

**Built in D1**
- **Definition** (`Dashboards/Definition.cs`): positional records (required in OpenAPI, so the client's types have no optional lists); `WidgetConfig` an abstract record with `[JsonDerivedType]`s `text`, `pie`, `bar`, `line`, `table`, and `DataWidgetConfig` (source, conditions, emits, listens) under the four of data. OpenAPI describes it as an `anyOf` with a discriminator, and `npm run api` gives a union to narrow on `config.kind`.
- **Rules** (`DefinitionRules`, `DefinitionCheck`): everything of §1 but the catalog's, by JSON path under `definition.`; lists too long are said once and their items checked all the same, so nothing else fails for want of them; links joined as a union-find (a cycle, or a pair twice, is the link that closes it). `WidgetKinds` (`IWidgetKind`, `WidgetKind<T>`) holds each kind's own rules: pie's "Other" for counts and sums, one measure with a series, sorts by index, raw and grouped tables, text up to 20,000 characters. The canonical form orders cells by widget id and writes numbers shortest (`ValueCodec.ShortestNumber`, moved from saved queries); `DefinitionJson` writes and reads it, and hashes it (SHA-256, hex).
- **Model** (migration `Dashboards`): as §3.1, `EmbedOrigins` a primitive collection. Settings `GalaxyData:Dashboards` (§3.7), checked at startup.
- **Endpoints** (`Features/Dashboards/DashboardEndpoints.cs`): as §3.3 but the data, query and filter-value ones (D3). An administrator's sharing request may only narrow (403 otherwise); a publish of nothing new numbers nothing; restore and discard set the working copy. `EmbedOrigin.Normalize` reads origins (lower case, international names as ASCII, `*.` subdomains, ports 1–65535) and writes them anew. Tokens are 22 base64url characters. Problems `dashboard-name-taken`, `public-dashboards-disabled`.
- **Tests** (`Dashboards/DefinitionRulesTests`, `DashboardApiTests`; 355 server tests pass): the canonical form and its hash; mistakes by field; links as a forest; each kind's rules; conditions' values by op; layouts within their columns and overrides; the kind read wherever it is, unknown kinds and enum numbers refused; sizes; visibility (unpublished shares unseen, viewers see the published copy only, owners' changes theirs until published, copies), administrators (shared and unpublished seen, private not, narrowing only), revisions (numbered, pruned to `KeepRevisions`, restored, discarded), no-op saves, names and versions, public links by role, origins, regeneration and revocation by administrators, a demoted enabler, the audit without tokens, `AllowPublic` off, a deleted owner's dashboards and shares, people found by name (case, display names, `_` literal, disabled users left out). The role matrix gains `/api/dashboards` and `/api/dashboards/people`; the OpenAPI snapshot and `schema.d.ts` are additions only.

### 3.2 Who sees and does what
A dashboard someone may not see is a 404 for everything; one they may see but not change, a 403.

| Who | Sees | May |
|---|---|---|
| Owner | the working and published copies | everything; making it public needs DataManager or Admin (403 otherwise) |
| Viewer (chosen, or everyone) | the published copy; unpublished, it is a 404 and not listed | save a copy |
| Admin | shared, public and orphaned dashboards (another's private one is a 404) | make private, unshare, revoke or regenerate the link, delete; edit and publish orphans; never make another's public |
| Anyone with the link | the published copy | 404 when the token is unknown, `Dashboards:AllowPublic` is off, nothing is published, or whoever made it public no longer may (gone, disabled, or a reader now); never 401 or 403 |

- Data, preview and query endpoints need `CanRead` (`SignedIn` lets users with a password to change through).
- **Audit** (`AdminAudit.Add`, in the same save): `dashboard.public.enabled`, `.regenerated`, `.revoked`, `.origins-changed`, and deletes of public dashboards; never the token.
- **Public links aren't access control for signed-in users, and hidden filters aren't row-level security:** a hidden filter narrows only the widgets linked to its source. The editor says both.

### 3.4 Widget queries (`Dashboards/`)
- **`ConditionWriter`**, extracted from `GridQueryComposer.Condition` (`Browse/GridQueryComposer.cs:132-222`) with **`QueryParameterAllocator`** (`:44-54`): `Write(target, type, displayName, condition, field, allocator, errors)` where `target` is the operand's text (`QuoteName(column)` for grids; `r0.customer.country` for dashboards), over an internal `ConditionOp` (the grid's ops plus `In`, `NotIn`, `Relative`). The public `GridOp` and browse's behaviour don't change (the grid, browse and query tests and the OpenAPI snapshot pass unedited).
  - `In`: `(x in [$f1, …])`, `or x == null` when null is listed (a null `$param` in the list never matches), `false` when empty; `NotIn`: `(not (x in […]) or x == null)`, or `(x != null and not (x in […]))` when null is listed; date-only values against date-times as an OR of day ranges.
  - `Relative`: a half-open range computed in C# from the app's `TimeProvider` in UTC (`DayStart` for the field's type), not `today()`, so cache keys turn over with the bounds.
- **`FieldResolver`:** a source's entity (`QueryCatalog.FindEntity`), each path step a forward, unhidden navigation (`FindNavigation`), then the column (`FindColumn`): its `ScalarType`, the text (`AppendMember`), or an issue.
- **Lambdas everywhere:** every generated condition is `where(r0 => …)` with each member written through `r0.` (row members hide catalog aliases otherwise), nested lambdas `r1`, `r2`…, each name given `_`s while `catalog.Root.Lookup(name)` finds something.
- **Which conditions reach widget W:** for each source S, `C_S` is the AND of the filters on S that apply to W, the selections of the widgets W listens to whose source is S (never W's own), and W's own conditions when S is W's source. Two widgets on one source combine inside one predicate ("customers with an open 2025 order", not "an open order and a 2025 order"). From W's source, the links are walked as a tree: `Cond(S, v) = C_S(v) and Hop(S → child, v, Cond(child, …))` for each child with conditions below it. Sources not linked to W don't reach it.
- **Hops**, one navigation at a time: to-one: `v.n` as the row (with `v.n != null` when it may be missing); a collection: `v.n.any(r1 => …)`; a step back into a virtual-entity source (whose inherited navigation's opposite is its base table): `<ve>.any(r1 => r1.<cols> == v.<cols> and …)`, as `NavigationResolver` writes its correlated form; `path: []` (two sources on one entity): `v` itself. **Meaning:** a linked widget keeps the rows related to at least one row that every condition on the other source keeps. Excluding "cancelled" on an orders chart leaves the customers with some order that isn't cancelled.
- **A selection** (emitter E, dimensions D, keys): include is an OR of keys, each an AND of its parts (one dimension: `x in [$s1, …]`, `or x == null` for a null key); exclude is `not (P)` with each part guarded so it is never null (`(x != null and x == $s)`, a bucket `(x != null and x >= $a and x < $b)`, a null `x == null`). ORs are written as balanced trees (the parser nests 256 levels). A bucketed key is its bucket's start, checked aligned (400 otherwise); the end is computed in C#; the condition is on the raw field (indexes still help) with parameters of the field's type (`DayStart`); cyclic buckets compare `quarter(x) == $s`. Keys decode through `ValueCodec` to the dimension's type.
- **`WidgetQueryBuilder`** per kind (an `IWidgetKind` registry, `AddWidgetKind<T>()`: `Validate(config, context)`, `Build(config, conditions, context)`). For a chart:

  ```
  (shop.orders).where(r0 => <conditions>).groupBy(d0: status, s0: …).select(d0, s0, m0: count(), m1: sum(total))
     .orderBy(desc(m0), d0, s0).take(<limit + 1>)
  ```

  - Conditions are lambdas (above); `groupBy` and `select` read the implicit row, with member names written through `QuoteName` and `AppendMember`.
  - Names are positional (`d0`, `s0`, `m0`): labels never need quoting or collide; the answer maps them to labels and roles.
  - Grouped results get no tie-break from the engine, so the sort always ends with the dimensions (guids, which can't be sorted, left out).
  - **Top N with a series:** the top N categories in a query of their own (`… groupBy(d0: …).select(d0, m: …).orderBy(desc(m), d0).take(N)`), then the data query filtered with `d0 in [$t1, …]` (`or … == null` when null is among them, which an `in` subquery would drop). **Pie "Other"** (count, countValues and sum only): a total (`groupBy().select(m0: …)`) minus what is shown. Each is its own cached query.
  - **Line:** ordered by x; at most `Dashboards:MaxChartRows` (10,000) points. **Tables:** grouped as a chart, paged by the engine; raw: the fields and the entity's key columns, sorted (by the key by default), paged; raw rows emit their key (not on public dashboards).
  - **The underlying query** (for the Data popup): the source with every condition that reaches the widget, no grouping.
- **Filter values:** a filter's field grouped, with every other condition reaching it (hidden filters included), `count()`, ordered by count then value, at most 100; searching text with `icontains` on text fields only; numbers and guids by equality when the term parses; dates not searched (ranges instead).

**Built in D2**
- **`Queries/ConditionWriter.cs`:** `ConditionWriter.Write(target, type, displayName, ConditionSpec, field, QueryParameterAllocator, errors, today)` and `QueryParameterAllocator` (`$f1`… as the grid named them), taken out of `GridQueryComposer`, which maps `GridOp` to `ConditionOp` by name and is otherwise as it was (browse, grid and query tests unedited). New: `in`/`notIn` (§3.4), `relative` (`Period`, `StartOf`, `Plus`: last n periods up to today, this, previous n, to date; weeks from Monday), `DayStart` for dates too.
- **`Dashboards/DashboardCatalog.cs`:** sources resolved (ambiguous and missing entities are issues), fields through forward navigations (own or inherited, exact case first; a collection is an issue), links both ways (`LinkHop`: the navigations, or their opposites back; `Correlated` when they land on the base a virtual entity filters), lambda rows `r0`, `r1`… with `_`s while the catalog's root has the name.

### 3.5 Running widgets
- **Inline (editor)**: a **slice** is a minimal definition: the widget, its source and linked sources, the filters reaching it, and the fields of the emitters it listens to; checked as a definition is. **Published:** the stored copy, by hash.
- **State:** `{filters: {id: condition value}, selections: {widgetId: {mode, keys}}}`; values of filters that aren't editable are ignored (their defaults hold), hidden filters always apply. At most `MaxSelectionKeys` (50; public 25) keys a selection and `MaxFilterValues` (500; public 100) values; refused with a 400 by field, never truncated. Request bodies ≤ 64 KB.
- **Answer** (`WidgetDataDto`): `columns` (`role`: dimension, series, measure, key, column; label; type), `rows` (positional, `ValueCodec`: int64 and decimals as exact text, the client turns them into numbers to draw), `truncated`, `total` and `offset` (tables), `other`, `refreshedAt`, `cached`, `hash`, `issues`. `…/query` answers `{text, parameters, underlying: {text, parameters}}`; the client explains through `POST /api/query/explain` and runs the underlying rows through `POST /api/query/execute`, which readers may already call.
- **Execution:** prepared with a `take` of the limit + 1 (`QueryRequest.Paging` for tables), `QueryRequest.Timeout = Dashboards:WidgetTimeout` (30 s; public 15 s), through the catalog's `QueryEngines`.
- **Cache** (`WidgetResults`, a `MemoryCache` of its own with a size limit, as the shared one holds session entries without sizes): keyed by the effective query (text, typed parameter values with offsets normalized to UTC, paging, the catalog version), so junk in a state can't make new entries and widgets asking the same share one; single-flight (the first caller leaving doesn't cancel the work); `CacheDuration` (30 s); failures kept 10 s. `refresh: true` (signed in) marks the entry stale and runs it once for everyone waiting.
- **Concurrency:** the `queries` rate limit (4 running, 16 waiting per user) covers these endpoints; the client keeps 4 widget requests in flight per page.

**Built in D3**

### 3.6 Public dashboards and embedding
- **Group `app.MapGroup("/api/public/dashboards")`**, outside the `api` group (so neither `AntiforgeryFilter` nor `CatalogVersionFilter` runs), `.AllowAnonymous()`, **GET only**, under the global rate limiter (per address): `GET /{token}`, `GET /{token}/widgets/{w}/data?s=&page=`, `GET /{token}/filters/{f}/values?s=&text=`. `s` is the state as base64url JSON, at most 4 KB; search text at most 200 characters. `PolicyTests` gains a check that every anonymous endpoint is one of the four sign-in ones or a GET under `/api/public`.
- **They read no user**, even when a signed-in user's cookies come along (an embed opened directly), and call `CatalogService.GetAsync(CancellationToken)` (the `HttpResponse` overload writes `X-Catalog-Version`).
- **Tokens:** an in-memory map from token to dashboard, refreshed on change; the published copy only, under the rules of §3.2.
- **What they give:** `PublicDashboardDto` holds the name, description, layout, widgets' kinds, titles and display settings, column roles and labels, the visible filters (label, kind, type, value, editable), the refresh policy and `showData`: no ids, entities, fields, links, conditions, hidden filters, origins, owner or revision. Data answers are `WidgetDataDto` without hashes or issue texts. `private, no-cache` with an ETag (304s are cheap).
- **Failures** are caught by the public service and answered as problems with codes alone (`widget-invalid`, `source-unavailable`, `query-timeout`, `too-many-requests`), and `ApiExceptionHandler.Describe` leaves out details for `/api/public` paths besides. Never 401 or 403.
- **Abuse:** always cached (`PublicCacheDuration`, 30 s); a timer refresh no shorter than that; a per-dashboard limit on queries actually run (`PublicQueriesPerDashboard`, 4 at once), in the service, so cache hits don't count; addresses limited as now (`Proxy:Enabled` matters behind a proxy, as every viewer would otherwise share its address).
- **Embed page:** `MapGet("/embed/{token}")` (outranks the client's fallback) looks up the token, sets an `EmbedFraming` feature and writes `index.html` (`no-cache`). `SecurityHeaders` reads the feature as the answer starts: no `X-Frame-Options`, the client policy's `frame-ancestors` replaced with `'self'` and the dashboard's origins (each validated as `scheme://host[:port]` or `*.host`, kept re-serialized, and allowed by `Dashboards:EmbedFrameAncestors`, `*` by default) or the setting itself, and `Cross-Origin-Resource-Policy: cross-origin`. An unknown or revoked token is framed under the setting, so the page can say it isn't available (it has no actions). Other pages keep `DENY`. Assets need nothing (same-origin to the frame).
- **Logs:** `SecretRedactor` masks tokens in `/embed/<t>` and `/api/public/dashboards/<t>` paths.
- **Cookies are `SameSite=Strict`**, so a cross-site iframe is always anonymous: only public dashboards embed. `docs/server.md` says so, with the iframe snippet and the settings.

### 4.2 Widget registry
`WIDGET_KINDS` (an `InjectionToken<readonly WidgetKind[]>` with the built-in kinds as its factory). A kind has `kind`, `label`, `icon`, `defaultSize` (columns of the designed breakpoint), `minSize` (pixels, turned into columns per breakpoint), `data`/`emits`/`listens` flags, `defaults(source)`, `view()` and `editor()` (lazy components rendered through `NgComponentOutlet`), and `issues?(config)`. ### 4.3 Layout engine (`layout/grid-layout.ts`, pure)
- **Model** (in the definition, §1): `layout {rowHeight, gap, breakpoints: [{id, label, minWidth, columns}] (ascending, the first at 0, the last designed), items: {widgetId: {x, y, w, h}}, overrides: {breakpointId: {columns, items, hidden}}}`.
- **Functions** (inputs never mutated):
  - `normalize` (clamp to bounds and minimum sizes, resolve overlaps in reading order by pushing down, compact); `compact` (vertical gravity, sorted by y, x, id; stored layouts are always compact).
  - `moveTo` (place at the clamped target; each collider swaps up above the mover when it fits there, else is pushed down and moves in turn; then compact). Pointer preview and keyboard use it, so a drop is what the preview showed; without the swap, compaction undoes downward moves.
  - `resizeTo` (clamp, push colliders down, compact); `place` (first fit from the top, for a new widget).
  - `derive(designed, fromCols, toCols)`: reading order (y, x, id); `w' = clamp(max(round(w·to/from), minColumns), 1, to)`, heights kept; monotone first fit after a cursor; **not** compacted afterwards, as compaction can break reading order. One column stacks in order.
  - `effectiveLayout(definition, breakpoint)`: the designed layout; or derived; or the override, with widgets removed since dropped, re-derived if the breakpoint's column count changed, and widgets added since placed after their nearest designed-order predecessor (returned, so the editor can say "2 widgets were placed automatically at Medium"); `hidden` removes widgets at that width.
  - `breakpointFor(width, breakpoints)`: the last with `minWidth ≤ width`; the widest when the width is unknown.
- **Properties** (fast-check, 400 runs, as `browse-url.spec.ts`): in bounds; no overlaps; the same ids; compact after every operation; idempotent `compact`/`normalize`; `derive(L, c, c) = L`; derive keeps reading order (one column: `y[i+1] = y[i] + h[i]`); `moveTo` to the current place is the identity; `breakpointFor` total and monotone; inputs deep-frozen.
- **Rendering: CSS grid** (`repeat(var(--gd-columns), minmax(0, 1fr))`, `grid-auto-rows: var(--gd-row-height)`, `grid-column: x+1 / span w`). Natural height (which the embed's auto-height needs), no script positions in view mode, DOM order sorted by (y, x) so tab order matches what is seen. Items also carry `data-gd-cell="x,y,w,h"` for tests.
- **Breakpoint from the container's width** (`elementSize`, ResizeObserver), with `scrollbar-gutter: stable` to avoid a scrollbar loop. jsdom has none: tests install `FakeResizeObserver` (`src/testing/resize.ts`).
- **Pointer drag and resize:** as the catalog splitter (`browse-layout.ts`: pointer capture, `touch-action: none`), throttled to animation frames; a placeholder at the `moveTo` result while the dragged widget follows the pointer by transform; Escape cancels.
- **Keyboard:** each frame's move handle (`aria-roledescription="movable widget"`): Enter or Space starts moving, arrows move, Shift+arrows resize, Enter commits (one undo entry), Escape restores. Each step is announced through `LiveAnnouncer` ("Sales by region: column 3, row 5, 4 by 6"); DOM order is frozen while moving, and focus returns to the handle after the re-sort. The Layout panel also has x/y/w/h fields.
- **Narrower widths in the editor:** a toggle per breakpoint constrains the canvas width and forces that breakpoint; "Follows the wide layout" with **Customize** (snapshots `effectiveLayout` into an override) or "Customized" with **Reset to derived**. Edits there only touch that override.

### 4.4 State and data (`state/`)
- **`DashboardStore`**, provided by each page (view, embed, editor): the definition; filter values and selections from `UrlState` (view, embed: a `linkedSignal` over the query params, written with `replaceUrl`, read back equal so nothing loops; back and forward work) or `LocalState` (editor).
- **Selections** per emitting widget: `{mode: 'include' | 'exclude', keys}`, a key being the slice's dimension values (one, or two with a series) as `ValueCodec` writes them. `selectionAfter(selection, action, key)`: a click replaces (clicking the only selected slice clears); Ctrl/⌘+click toggles in include mode (OR within the chart); Alt+click toggles in exclude mode; include and exclude never mix, so chips read as sentences ("Status: open, shipped", "Region: not EMEA").
- **Each widget's inputs** (`computed` with structural equality): the non-empty values of filters that apply to it, and the selections of the emitters it listens to (never its own). An unrelated change never reaches the widget's resource, so nothing else is fetched again; an emitter's own selection changes only its highlight.
- **Loading:** `rxResource` per widget through `DASHBOARD_HOST.data(inputs)`; a new input cancels the request before (`HttpClient` aborts it). Rows shown are kept while loading (`linkedSignal`, a thin progress bar) and after a failure (with "Couldn't refresh: … (data from 10:42)").
- **`DASHBOARD_HOST`** (`data`, `filterValues`, `query`, `canViewQueries`, `canViewUnderlying`, `kind: app | embed | editor`): the view never injects `AuthStore`. `DashboardPage` provides it from the session (the published copy through `…/{id}/widgets/{w}/data` with its hash, a 409 `dashboard-changed` loading the dashboard again; the owner's working copy through the inline endpoint); the embed with constants and the public GETs (state as the `s` parameter); the editor with the inline endpoint. Each host keeps at most 4 requests in flight per page (the server's `queries` limit is 4 running and 16 waiting per user).
- **Editor preview:** a widget's **slice** (`model/slice.ts`: the widget, its source, the filters that apply to it, the fields of the emitters it listens to) is both the request body of `POST /api/dashboards/data` and the resource key, debounced (`DASHBOARD_WAITS {preview: 400, filterTyping: 300}`, 1 ms in tests), so editing another widget's title fetches nothing.
- **Refresh** (`refresh.ts`, after `pollWhile`): Refresh reloads every widget; on a timer, `setTimeout` from an effect over the policy, page visibility (`page-visibility.ts`) and whether anything is loading: nothing while hidden or loading (no overlap), longer waits after failures (doubling to 5 minutes; a 429's `Retry-After` first), and at once when shown again after the interval. "Refreshed 2 minutes ago" in the bar. The editor refreshes by hand.
- **URL codec** (`core/dashboards/dashboard-url.ts`), in `browse-url.ts`'s conventions (grammar in the header comment, a writer, `read…` giving `{value, problems}`, `'…'` quoting with a scanner, fast-check round trips through `DefaultUrlSerializer`): `f.<filterId>=a,b` (a range `from~to`, either side empty; bare `null` is NULL, `'null'` the text), `s.<widgetId>=k1,k2` (`!` first for exclude mode; a two-part key's values joined by `|`, quoted when they hold the marks), and `theme=` in embeds. Only values unlike the defaults are written; unknown ids, locked or hidden filters and malformed values are problems and left out (the server enforces locked filters anyway). Ids are `[a-z0-9-]{1,32}`, so keys need no quoting.

### 4.8 Popups

**Built in D6**
- **Address** (`core/dashboards/dashboard-url.ts`): `f.<filter>` by kind (values `a,b`, `!` for those left out; ranges `from~to`; periods `last.7.day`; text; booleans) and `s.<widget>` (`!` for left out, `|` between a slice's parts). ### 4.9 Editor (`editor/`)
- `EditorStore`: saved and draft definitions, version, history, the selected widget, the breakpoint shown, issues. Every edit is a pure function of `definition-ops.ts`, applied with a label and a coalescing key.
- The canvas is the shared view in edit mode (an **Interact** toggle tries selections); side tabs: **Widget**, **Sources**, **Filters**, **Layout**, **Refresh**, **Issues**; a palette adds Text, Pie, Bar, Line and Table (placed by `place`).
- **Widget config:** one lazy component per kind with `config = model.required<C>()` and a signal form over it (`required`, `validate`, `applyEach` for lists, `readonly` while saving), so undo (which sets the draft) needs no effects. Bar: dimension (with a date bucket), optional series, measures (aggregate + field; one when there is a series), orientation, stacked, sort, limit, labels, legend, axis titles, number format. Line: x (bucket), series, measures, area, gaps (zero, connect, break). Pie: category, measure, limit, "Other", donut, labels. Table: grouped or raw, columns or dimensions and measures, sort, page size. Text: Markdown. Every chart: title, the conditions of its own, which filters apply, emits, listens to (all, none, chosen widgets).
- **Field picker** (`{path, column}`): an autocomplete in the overlay's style (`customer.country`), over an editor-wide `EntityCatalog` (a cache of `/api/catalog/entity` resources, following catalog changes); columns that aren't hidden, and forward navigations (one or zero-or-one, not hidden); allowed types by role (numbers for sums and averages, sortable types for dimensions).
- **Sources:** entities found through `EntitySearch`, with labels; links between sources with their paths ("orders → customer"), suggested by `GET /api/catalog/paths` and chosen among several; an issue for widgets whose emitters' sources aren't linked to theirs, and a refusal of links that would make a cycle.
- **Filters:** label, field (per source), kind, default, visible, editable, multiple, and the widgets it applies to; values offered from the server as typing pauses.
- **Layout:** breakpoints (ascending, the first at 0, 1–24 columns), row height, gap, the width toggle with Customize and Reset. **Refresh:** manual, or every N seconds (at least the server's minimum).
- **History:** up to 100 entries; edits with the same key within a second coalesce (typing is one entry, a drag is one, on drop); Ctrl+Z, Ctrl+Shift+Z/Ctrl+Y outside inputs, editors and grids (as `query-page.ts`); announced ("Undid: moved Sales by region").
- **Saving:** Ctrl+S, `PUT` with the version (or `POST` when new); 409 offers "Read it again" or "Save as a copy" (as the query editor); 400s placed on their fields by JSON path, the rest in Issues; `unsavedChangesGuard`, `warnBeforeUnload`, "(edited)" in the title.
- **Issues:** the client's (kinds, forms, auto-placements, unlinked sources) and the server's (per widget, from previews and saves), each with Go to.
- **Dialogs** (signal forms, as `save-query-dialog.ts`): Publish (a note; says what changed since the last revision); Revisions (list, view, restore into the working copy, discard changes); Share (private, chosen users found by name, everyone, public with its link, the iframe snippet, Regenerate and Revoke after confirming, and embedding origins; public offered only when the server allows it for this user).

**Built in D7**
- **Routes:** `new` and `:id/edit` (`unsavedChangesGuard`); a new dashboard's first save goes to `:id/edit` (`replaceUrl`), whose editor reads it (the history starts again there).
- **Model** (pure, tested): `definition-ops.ts` (widgets added where they fit at every laid-out breakpoint, copied, removed with all that names them; moves and resizes at a breakpoint; `customize`, `resetBreakpoint`, `hideAt`; breakpoints replaced, the designed cells scaled; sources, links refusing cycles (`wouldCycle`), filters, refresh); `slice.ts` (`sliceOf`: the widget without its title, its linked sources and their links, the filters with fields that apply to it, and of the widgets it listens to **only those something is chosen in**, as their dimensions; cells stacked, no overrides); `complete.ts` (`missingOf`: what a widget being made still needs).

### 4.11 Embed page (`embed/`)
- Outside the Shell, inputs `token` and `theme`; a `main` with the hidden `h1`, the filter bar and chips (when there are any), Refresh (manual policy, a small button), and the grid; no query views or underlying rows. The document's title is the dashboard's name.

- **Problems, never a sign-in prompt:** 404 "This dashboard isn't available. It may no longer be public." (the server answers 404 for every reason, revealing none); 429 with its wait; unreachable with Try again; widget problems in their frames by code.

- **Dialogs** (`dialogs/`, imported when opened): Publish (what changed since the last revision, `changesBetween`; a note); Revisions (restore, after asking when there are changes; discard); Copy (a name; opens the copy); Share (only you, chosen people found as typing pauses, everyone signed in; the public link for those who may make it or revoke it: the link, the iframe snippet with its height listener checking `event.origin`, copying either, sites that may frame it with refusals said by line, a new link and stopping it after asking; the toggle shows what is till the server answers). ## 7. Risks and mitigations

- **Cross-filter meaning through one-to-many links** ("customers with some order that isn't cancelled"): defined once (§3.4), tested both ways, and said in `docs/client.md` and the editor's link panel.
- **Anonymous load on sources:** always cached, single flight, a per-dashboard limit on queries run, timer floors, and per-address limits (which need `Proxy:Enabled` behind a proxy; `server.md` says so).
- **Leaking internals publicly:** a separate DTO, failures by code alone, `Describe` stripped, a test over every public answer, tokens masked in logs. Hidden filters aren't row-level security; the editor says so.
- **Canvas charts aren't accessible:** the table alternative with its buttons and the selection chips are part of D6, not polish.
- **Bundle budget (721 of 750 kB):** everything lazy; the initial bundle grows by a few kB, measured in D5. Making the Shell lazy is the fallback if it is ever needed.
- **ECharts and the CSP:** no `'unsafe-eval'`, so the build scans the chunks for `eval` and `new Function`; tooltip HTML escaped.
- **Layout corner cases:** fast-check properties over the pure engine; overrides fall back to derivation when breakpoints change.
- **Per-user request limits:** 4 in flight per page on the client; a batch data endpoint is the escape hatch if pages with many widgets feel slow.
- **SQL Server's 2,100 parameters:** the engine already writes constants past the limit; the parser's depth (balanced ORs) and the query length are the real limits, guarded by the selection and value caps.

# Part 2 — Series palettes (D10–D13)

## Context

Chart colours today follow categories only while a page is open (D9's first known limitation): each chart widget keeps a `ColorMemory` (`charts/chart-options.ts`) handing out the eight `--gd-chart-*` colours in the order it first meets slices, series or measures, grey past the eighth. So "cancelled" is red in one chart and blue in the next, and changes after a reload. Users associate labels with colours, so we add **series palettes**: named sets of colours users create, which a dashboard picks as the default for its charts, with a per-chart override. A palette colours labels by their order, or by their label (a hash: the same label always gets the same colour), with per-label overrides and matching that can ignore case, whitespace, accents and text in brackets. A new palette starts from a built-in base, and overrides are added from the data.

**Decisions confirmed with the user**
- **A shared library:** anyone who reads data creates palettes; everyone signed in sees and uses every palette; only its owner and administrators change or delete it.
- **Live references:** dashboards refer to palettes, so editing one recolours every dashboard using it, published copies included (the queries and layout stay as published).
- **Dark mode:** each colour has a light value and an optional dark one (the light one otherwise); the bases come with both; the editor warns about low contrast on either surface.
- **Bars by category:** a bar chart of one measure and no series gets a per-chart "Colour bars by category" (off by default), so a status's colour is the same in a bar chart as in a pie.

**Out of scope:** per-chart overrides of single labels (overrides live in palettes, so they stay consistent), sequential and diverging palettes (magnitude and polarity), colours for tables' cells, colours from status meanings.

---

## 8. Palettes and matching

A palette is a named, owned row holding one JSON definition, typed on both sides as the dashboard's is:

```jsonc
{
  "colors": [ { "light": "#2a78d6", "dark": "#3987e5" }, { "light": "#eb6834", "dark": null } ],  // dark null: the light one
  "assign": "label",           // "order": by first meeting in a chart; "label": by a hash of the label
  "distinct": true,            // within a chart, what would share a colour with another takes the next one free
  "whenOut": "repeat",         // past the last colour (order), or none free (distinct): "repeat" or "neutral" (grey)
  "matching": { "ignoreCase": true, "ignoreWhitespace": false, "ignoreBrackets": false, "ignoreAccents": false },
  "overrides": [ { "label": "cancelled", "color": { "light": "#e34948", "dark": "#e66767" } },
                 { "label": null, "color": { "light": "#9a9ca3", "dark": null } } ]   // null: no value
}
```

- **A new palette** colours by label, distinct, repeating when colours run out, ignoring case (its base gives the colours).
- **Rules** (by JSON path, `definition.overrides[3].label`, as dashboards'): 1–32 colours, `#rrggbb` (lower case in the canonical form; no alpha, as fading a slice is opacity); at most 500 overrides; labels up to 200 characters; the JSON at most 64 KB (a dashboard's answer carries the palettes it names, §10.3); a label that normalises to nothing ("(EMEA)" with brackets ignored) is refused, and so is a second override matching what an earlier one matches (naming it). The canonical form and its SHA-256 hash as dashboards' (`DefinitionJson`'s options).
- **A label's text** is what it is matched by: a value as the answer carries it (text as it is; int64 and decimals are text already; other numbers as ECMAScript's `Number::toString` writes them, which the server copies (`1e+21`, not .NET's `1E+21`); booleans `true` and `false`; dates and periods as ISO, so January's bucket is `2026-01-01`, and cyclic buckets as their numbers, Monday `1`), or a measure's label; no value (null) matches only the override for no value. Never the shown text ("Jan 2026", "Monday", "(no value)"), which depends on the locale; the editors show it beside the label.
- **Normalisation** (`LabelMatching`, the same in C# and TypeScript): NFC; trimmed; brackets (text in `()`, `[]` and `{}` removed with them, nested, each closing only its own kind; one never closed, or a closing one never opened, kept as text); accents (NFD, combining marks removed, NFC again); case (each code point's simple lowercase: `Rune.ToLowerInvariant` in C#, the first code point of each code point's `toLowerCase()` in TypeScript, so `İ` and a final sigma agree); whitespace (removed altogether, so "Cape Town" matches "CapeTown"); trimmed again. Whitespace and trimming use one explicit class of characters on both sides (JavaScript's `\s` has U+FEFF and not U+0085; .NET's `char.IsWhiteSpace` the reverse). One fixture of cases (`tests/fixtures/palette-labels.json`: text, options, expected; and values with their label texts) is read by both test suites (the test project copies `*.json` fixtures too).

## 9. Assigning colours (client, `charts/series-colors.ts`, pure)

- **What is coloured:** pie slices (the dimension's values; "Other" is always grey and takes no colour); bars' and lines' series values when there is a series, else their measures by label; a bar chart's categories when it has `colorBy: "category"` (each bar its own `itemStyle.color`, merged with the selection's look; the legend is already hidden for one series, and the axis names them).
- **Gather, then assign:** `coloredEntities(config, data)` lists what a chart colours, in the order the builders meet them today (`keyText([v])` for slices, `'measure:' + label`, `'series:' + keyText([v])`, and a new `'category:' + keyText([v])`), each with its label text and shown text. `ChartContext.colors` becomes an interface (`color(entity, theme)`): `ColorMemory` stays as the one without a palette (so its tests hold), and a palette's assignment is the other. The chart widget works the assignment out in a `computed` of the config, the rows, the palette, the scheme and the answer's `colors`, needing neither the chart's instance nor the selection, so the table view and a chart that couldn't load get the same colours. A property test: every entity a builder asks for is listed.
- **Steps:** (1) overrides, by normalised text (embedded: the answer's `colors` instead, §10.4); they never move and take no slot. (2) The rest: **order**: slots by first meeting; **label**: a jump consistent hash (Lamping and Veach; `BigInt`) of the FNV-1a 64 of the normalised text's UTF-8, over the number of colours, so adding a colour at the end moves only the labels the new one takes (reordering or removing colours moves others: the palette editor says so). (3) **Distinct**: what would take a colour already taken in this chart (by an override, or by what came before: in order of meeting for order, of normalised text for label) takes the next colour not taken, in the palette's order. (4) None free, or past the last colour: `whenOut` (`repeat` cycles; `neutral` is grey).
- **Kept while shown:** what a widget has coloured keeps its colour while it is shown (one memory per widget, started again when its palette, its palette's hash, `colorBy` or the coloured field changes), so a filter that leaves some out doesn't paint the others anew (the rule `ColorMemory` was written for); label colours and overrides also agree across charts, dashboards and reloads, but for what distinct moved.
- **Dark:** `dark ?? light` under a dark scheme.
- **No palette** (neither the chart nor the dashboard names one, or the one named is gone): exactly today's colours (the theme's eight by order, grey after).

### 10.1 Model (migration `Palettes`)

## 14. Risks
- **Label mode collides** (eight colours, six slices: most pies would share one): `distinct` on by default, overrides, and the checks' all-pairs warning.
- **C# and TypeScript normalising differently:** one shared fixture, with accents, `İ`, sigma, brackets nested, mismatched and unbalanced, whitespace of several kinds (U+00A0, U+0085, U+FEFF), and numbers' texts.
- **A palette's edit changes published dashboards** without publishing: chosen with the user; the palette editor says how many dashboards use it, and the publish dialog that palettes follow.
- **Leaks:** public views get no override, palette name or owner; answers only the colours of the labels they show, by their own text.
- **Hashes of saved dashboards:** the new fields are left out when unset, tested byte for byte, so nothing reads as changed.
- **Cycling repeats colours** (the dataviz method says never cycle): `whenOut: neutral` is there, the bases have at most eight colours, and pies keep their limit and "Other".
- **Pages open while a palette changes:** they follow when they refresh, or when reloaded; `client.md` says so.
